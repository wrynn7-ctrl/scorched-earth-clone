# Building Craterline for Android

Short version: run `tools/build_android_debug.sh` to get a phone-installable APK, and `tools/build_android_release.sh`
to get a release-style AAB. CI does the same on every push. Nothing here needs a secret yet.

## What is a "Gradle build" and why do we need it?

Godot can export an Android app in two ways:

1. **Prebuilt template (the old way).** Godot takes a ready-made APK, drops the game inside and signs it. Fast and simple,
   but you cannot add any Android code to it.
2. **Gradle build (what we use now).** Godot unpacks a small Android Studio style project (the "Android build template",
   in `game/android/`) and runs Gradle, the standard Android build tool, on it. Gradle can then add extra Android
   libraries to the app.

We need option 2 for **Google Play Billing**, the library behind in-app purchases (the "Full game" unlock, see
`docs/ARCHITECTURE.md` section 32). The billing plugin is Android code, so it can only be added through Gradle. Gradle
also produces the **AAB** (Android App Bundle), the file format Google Play requires for new apps.

Both export presets in `game/export_presets.cfg` use Gradle, minimum Android 8 (SDK 26), target SDK 36:

| Preset | Output | Used for |
|---|---|---|
| `Android` | `build/craterline-debug.apk` | testing on your phone (the `dev-latest` download page) |
| `Android Release` | `build/craterline-release.aab` | proving the Play pipeline; later the Play upload |

`game/android/` is generated by the scripts and is **not** in git (it is about 1 GB). Delete it any time; the next build
recreates it.

## The billing plugin

- Plugin: godot-sdk-integrations/godot-google-play-billing, version **3.3.0**, commit
  `e494f370ee591fa11823ad2749a070ed1149de99`, Play Billing Library 9.1.0 (needs Godot 4.2 or newer, works with 4.7.2).
- It lives in `game/addons/GodotGooglePlayBilling/` and is switched on in `game/project.godot` (`[editor_plugins]`).
  It provides `BillingClient` (a GDScript class) for the game and tells Godot's exporter to add the plugin's AAR and
  the `billing-ktx` library to the Android project.
- The pin is in `tools/billing/pin.env`; the SHA-256 of every vendored file is in `tools/billing/SHA256SUMS`. The two
  AARs are only about 40 KB together, so they are committed. The upstream project publishes no checksums, so we build them
  from the pinned commit; the build is reproducible (same hashes every time).
- `tools/setup_billing_plugin.sh` checks the files against the pins (both build scripts run it).
  `tools/setup_billing_plugin.sh --rebuild` rebuilds them from source.
- `.github/workflows/mirror-plugins.yml` rebuilds the plugin in CI and attaches it to the release
  `tools-billing-3.3.0` in this repo (run it once from the Actions tab: "Mirror plugins", "Run workflow"). Nothing needs
  that release to build the game; it is a convenience copy.
- To upgrade: change `tools/billing/pin.env`, run `tools/setup_billing_plugin.sh --rebuild` (it exits with code 3 and the
  new hashes if they differ), copy the new hashes into `tools/billing/SHA256SUMS`, and update the version above.
- Exported builds exclude the unit tests, GUT and the billing plugin's editor-only script (`exclude_filter` in the preset).

## Building locally

```bash
tools/build_android_debug.sh     # APK, signed with the public debug key, checked with apksigner
tools/build_android_release.sh   # AAB, ALSO signed with the public debug key (see below), checked with bundletool
```

Needs: Java 17 or newer, `curl`, `unzip`, internet access. Everything else (Godot, export templates, Android SDK pieces,
Gradle, the Android Gradle plugin, the Play Billing library, bundletool) is downloaded and pinned by the scripts. The
first run downloads a few hundred MB and takes a few minutes; later runs take 20 to 60 seconds (Gradle caches in `~/.gradle`).

Internet hosts used: this repo's GitHub Releases (Godot and templates), `dl.google.com` (Android SDK, Google Maven),
`repo.maven.apache.org` (Maven Central), `plugins.gradle.org`, `services.gradle.org` (which redirects to GitHub for the Gradle
download). Maven Central sometimes answers "429 Too Many Requests" for a moment; the scripts retry automatically.

A harmless line `ERROR: [GUT] Could not get version info` appears in the export log: GUT's editor plugin checks GitHub for a
newer GUT version when Godot loads the project. It does not affect the build.

## How CI builds it (`.github/workflows/ci.yml`)

1. **Tests** run first (four parallel legs).
2. **android-debug** builds the APK with `tools/build_android_debug.sh`, uploads it as the artifact
   `craterline-debug-apk`, and on the dev branch the `publish-dev-release` job puts it on the `dev-latest` page. The phone
   install is still the APK.
3. **android-release-aab** (dev branch pushes only, runs next to the APK job) builds the AAB with
   `tools/build_android_release.sh` and uploads it as the artifact `craterline-release-aab-debug-signed` (kept 14 days).
   It is **never** published to a release.
4. Gradle downloads are cached (`~/.gradle/caches/modules-2` and the Gradle distribution). The cache key changes when the
   Godot version, the billing pin or the export presets change.

## Signing: read this before uploading anything

The AAB is signed with the **public debug key** that is committed in `tools/android/debug.keystore`. That key is only for
testing: anyone can sign an app with it. **Google Play will not accept such a bundle, and you must not try to use it.**
The build script prints a large warning every time. **Real Play signing (an upload key kept in GitHub Actions secrets,
plus Play App Signing in the Play Console) is set up in milestone M8**, and until then no secret exists or is needed.
When M8 arrives the scripts pick the key from `GODOT_ANDROID_KEYSTORE_RELEASE_*` environment variables, so nothing secret
is ever stored in the repo.

`package/unique_name` (`com.wrynn7.craterline`) must be final before the first Play upload; it can never change afterwards.
